# Upstream References

## Purpose

Local upstream checkouts provide the implementation and test references for
compatibility work. They are development inputs, not runtime dependencies and
are never committed to this repository.

Ordinary users installing `gotpl`, `goduration`, or `gotime` do not need these
checkouts. Contributors need them only for oracle-backed compatibility work and
the complete repository gate.

## Pinned References

| Reference | Revision | Local path |
| --- | --- | --- |
| Go standard library | `go1.27.0` | `.references/go` |
| Masterminds Sprig | `v3.3.0` | `.references/sprig` |
| Go Task Slim-Sprig | `v3.0.0` | `.references/slim-sprig` |
| Go Sprout | `v1.1.1` | `.references/sprout` |
| Helm | `v4.2.3` | `.references/helm` |

The Go checkout is sparse and contains `src/text/template` and
`src/html/template`. The function-library checkouts contain their complete
repositories at the pinned tags.

The conformance tools isolate module graphs that have conflicting transitive
versions. In particular, `tools/sprig_oracle` uses Sprig v3.3.0's own module
graph, while the combined ecosystem oracle may use Sprout v1.1.1's newer
versions. This prevents Go's minimum-version selection from silently changing
the observable Sprig baseline when another reference is added.

The committed `_unicode_tables.py` artifact is generated from Go 1.27.0's
`unicode.Categories`, `unicode.Scripts`, and `unicode.CategoryAliases` maps.
It pins Unicode 17.0.0 behavior across supported Python versions. Regenerate
and verify it with:

```console
go run tools/generate_regex_unicode/main.go \
  src/gotpl/_compat/goregexp/_unicode_tables.py
./scripts/check_generated.sh
```

The generated artifact is covered by the Go BSD license notice in
`THIRD_PARTY_NOTICES.md`.

Sprout's versioned function, alias, notice, and group inventory is generated by
the pinned v1.1.1 Go module rather than inferred from documentation. Verify both
the report copy and packaged runtime resource with:

```console
./scripts/check_sprout_inventory.sh
```

Create the checkouts with:

```console
./scripts/sync_references.sh
```

The script refuses to replace an existing checkout at a different revision.
Remove or move such a checkout deliberately before rerunning it.

## How to Use the References

Compatibility work starts by locating the relevant upstream behavior:

1. Read the upstream public documentation.
2. Find the closest upstream implementation and tests.
3. Run or isolate the upstream case when practical.
4. Add an independently reviewable conformance fixture or Python test.
5. Confirm that the new pygotpl test fails for the intended reason.
6. Implement the smallest behavior that makes it pass.
7. Refactor only while the complete suite remains green.

The most important upstream test locations are:

```text
.references/go/src/text/template/*_test.go
.references/go/src/text/template/parse/*_test.go
.references/go/src/html/template/*_test.go
.references/go/src/time/*_test.go
.references/sprig/*_test.go
.references/slim-sprig/*_test.go
.references/sprout/registry/**/*_test.go
.references/sprout/group/**/*_test.go
.references/helm/pkg/engine/*_test.go
.references/helm/pkg/chart/v2/**/*_test.go
```

The planned translation order and Python-specific companion suites are mapped
in `docs/upstream-test-map.md`.

Use upstream tests to discover edge cases, error semantics, security behavior,
and historical regressions. Do not copy test bodies mechanically. Translate
behavior into the project's data-driven conformance format and retain enough
metadata to identify the upstream reference and revision.

## Licensing and Attribution

The local checkouts retain their upstream licenses. Copying or adapting source,
test code, test tables, or substantial fixtures into this repository requires a
license and attribution review first. Record the source revision and file for
every derived artifact. `docs/licensing.md` defines the review procedure,
fixture metadata mapping, and distribution notice requirements.

## Updating References

Reference upgrades are compatibility projects, not routine dependency updates.
An upgrade requires:

- A dedicated change to the pinned revisions in the bootstrap script and docs.
- A complete differential conformance run.
- A report of new, changed, and removed behavior.
- Updated benchmark baselines where implementation behavior changed.
- An update to `docs/compatibility.md`.
